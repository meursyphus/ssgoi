# 페이지 전환 매칭 구현 — 설명용 맥락

관련 이슈: [#409](https://github.com/meursyphus/ssgoi/issues/409). 구체적인 인터페이스·근거·검증 범위는 [영문 설계 문서](./05-motion-continuity.md)에 정리했다.

## 무엇을 구현하려는가

SSGOI는 페이지 전체의 전환을 관리한다. A에서 B로 이동 중 다시 A로 돌아가거나 C로 갈 때, 화면에는 A와 B가 모두 남아 있을 수 있다. 여기에 공유 이미지, 블라인드 패널, 배경 흐림이 서로 다른 속도와 순서로 움직인다.

이때 새 효과를 고르는 것만으로는 충분하지 않다. 지금 보이는 요소를 누가 이어받을지, 아직 들어오는 B를 어떻게 다시 내보낼지, 옛 패널은 언제 없앨지까지 관리해야 한다.

기존 코드는 이전 애니메이션을 강제로 완료하고 새 애니메이션을 실행했다. 복합 애니메이션의 매칭은 비어 있었다. 진행률을 전달해도 slide의 40%와 zoom의 40%가 같은 위치를 뜻하지 않으므로 공통 좌표에서 연결해야 한다.

## 새 효과가 늘어나도 유지되는 규칙

`drill 다음 zoom이면 이렇게`, `zoom 다음 blind이면 저렇게` 하는 조합별 처리표는 만들지 않는다.

Host는 현재 참여 중인 대상과 퇴장 중인 대상을 기억한다. 각 효과는 자신의 경로와 실행 순서를 정의하고, 다음 정보가 필요한 경우에만 선언한다.

- **키:** 다른 DOM으로 바뀌어도 같은 사진인지 등, 의미 있는 대상 식별자.
- **역할과 좌표 공간:** 페이지인지 공유 이미지인지, 어느 공간에서 계산한 값인지.
- **수명:** 계속 남을 페이지인지, 전환을 위해 만든 임시 패널인지.
- **표현:** 기본 웹 표현으로 충분하지 않으면 위치·속도를 읽고 쓰는 codec.
- **퇴장 정책:** 기본 페이드, 즉시 제거, 또는 그 효과가 정의한 자기 자신의 퇴장 애니메이션.

새 효과는 이전 효과들의 이름을 몰라도 된다. 매칭 엔진은 의미를 추측하지 않는다. 사진 42와 사진 99를 같은 대상으로 연결하지 않고, 가로 패널 10개와 세로 패널 20개를 같은 인덱스라는 이유로 연결하지 않는다.

## 연결은 어떻게 되는가

1. 이전 화면의 **최종 출력 상태**를 읽는다. 이미 진행 중인 보정도 포함한다.
2. 같은 DOM 또는 명시적인 공유 키를 찾는다. 역할·좌표 공간이 맞아야 하고, 중복 키는 임의로 고르지 않는다.
3. 위치·회전·크기·속도를 공통 표현으로 바꾼다. 페이지의 transform origin과 퍼센트 이동, 공유 이미지의 서로 다른 크기도 고려한다.
4. 새 효과의 경로와 현재 상태 사이의 차이를 보정값으로 넣는다.
5. 새 경로를 따라가면서 보정값을 일정 시간에 걸쳐 없앤다.

예를 들어 오른쪽으로 움직이다 왼쪽으로 돌아가라는 요청이 오면, 잠깐 오른쪽으로 더 움직이고 감속한 뒤 돌아갈 수 있다. 속도를 무조건 0으로 끊지 않는다. 같은 이중 스프링을 반전할 때는 겉으로 보이는 값뿐 아니라 내부 리더 스프링 상태도 유지한다.

수학적인 보정은 위치와 속도를 이어주지만, 실제 브라우저는 샘플링한 키프레임을 재생한다. 모든 픽셀의 순간 속도를 완벽히 증명했다는 뜻은 아니다.

## 취소와 정리를 분리한 이유

이전 **계획**이 취소됐다고 그 계획이 쓰던 모든 **요소**를 지워서는 안 된다. 다음 계획이 같은 B 페이지를 이미 이어받았을 수 있기 때문이다.

- 아직 시작하지 않은 옛 단계는 무효화한다.
- 새 계획이 가져가는 대상은 현재 상태로 넘긴다.
- 페이지는 남지만 특정 효과만 필요 없어졌으면 기본 상태로 돌아간다.
- 필요 없어진 임시 요소는 자신의 퇴장 규칙을 실행하고 제거한다.
- 정리는 현재 소유권이 있는 요소에만 적용한다.

그래서 `onComplete`는 정상적인 목표 도달이고, `onDispose`는 자원 정리다. 이전 실행의 정리가 새 실행의 스타일이나 DOM을 망가뜨리면 안 된다. 비동기 준비에도 세대 번호와 취소 신호를 넣어, 늦게 끝난 이전 요청이 최신 화면을 덮어쓰지 못하게 했다.

## 다른 라이브러리도 취소하고 넘기는가

그렇다. 다만 **실행을 취소하는 것과 현재 시각 상태를 버리는 것은 다른 문제**다.

Compose는 기존 실행을 취소하면서 현재 값·속도로 새 실행을 시작한다. Flutter Hero는 진행 중인 공유 요소의 비행을 새 목적지로 돌리고, 오버레이의 수명도 관리한다. Flutter의 페이지 전환은 새 페이지가 이전 페이지의 퇴장 동작을 제공할 수 있다. 게임의 inertialization은 새 경로와 현재 자세 사이의 차이를 유지하다 줄인다.

모든 라이브러리가 항상 속도를 완전히 유지하는 것은 아니다. 조사한 Motion 레이아웃 경로는 진행률 속도를 0으로 시작한다. Reanimated 4.6.0의 해당 스프링 경로는 새 목표와 반대 방향의 속도를 잘라낸다. SSGOI는 지원하는 표현에서는 기존 관성을 이어가는 쪽을 선택했다.

## 폴백도 정상적인 동작이다

의미가 불명확하거나 표현이 호환되지 않으면 억지 매칭을 하지 않는다.

- 키가 없거나 중복되면 새 요소는 등장하고 기존 요소는 퇴장한다.
- CSS 표현이 호환되지 않으면, 가능한 경우 이전 모습을 비활성 DOM 복사본으로 유지하고 크로스페이드한다.
- 캔버스·영상·iframe처럼 복사하면 상태가 달라지는 콘텐츠나 정확한 좌표를 확보할 수 없는 경우에는 즉시 완료 폴백을 사용한다.
- 효과가 제공한 퇴장 함수가 실패하면 공통 페이드로 대체한다.
- 기존 사용자 정의 애니메이션이 새 계약을 구현하지 않았으면 기존 완료 방식으로 처리한다.

어떤 대상이 연결됐고 왜 폴백이 선택됐는지를 디버그 이벤트로 확인할 수 있다. 임시 효과를 끝없이 남겨두지 않도록 퇴장 중인 실행 수에도 상한을 둔다.

## 현재 드래프트를 볼 때의 기준

모든 내장 효과와 주요 변형을 조합한 19×19 브라우저 검사를 만들었다. 전환 직전·직후 페이지 사각형, 유한한 CSS 값, 대상 매칭을 검사한다. 왕복 이동·공유 요소·블라인드 단계 취소·비동기 준비 경합·정리와 폴백도 별도로 검증한다.

이 결과가 곧 모든 환경에서 출시할 준비가 됐다는 뜻은 아니다. 실제 iOS Safari, 전환 중 레이아웃 변화, 변형된 조상 좌표계, 임의의 3D 장면, 네이티브 렌더러에는 추가 검증 또는 어댑터가 필요하다. 이번 PR은 공통 규칙을 실제 코드와 재현 시나리오로 검토할 수 있게 만드는 드래프트다.

## 리베이스·리뷰 반영 사항

7.2.0 이후의 `latest`(`cb48248`) 위로 리베이스했다. 그 사이 들어온 스크롤 잠금(#418)과 in-place hero(#415, #416)는 대체하지 않고 이 계약 위에 합쳤다.

- **스크롤 잠금**은 이전 준비를 무효화하기 전에 먼저 잡고, 실행이 끝나는 경로(정상/퇴장 후 정리, attach 전 무효화, 실패, 5초 준비 시간 초과) 중 하나에서 정확히 한 번 푼다. 퇴장 중인 실행은 퇴장 애니메이션이 정리될 때까지 잠금을 유지하고, 새 실행은 이미 자기 잠금을 들고 있다.
- **in-place hero**는 실제 목적지 이미지가 영속 트랙이고 사진 키(`shared-media`)를 가진다. 복사본은 키가 없어(`shared-media-source`) 절대 매칭되지 않는다. 그래서 A→B→A처럼 되돌아가면 비행이 새 목적지 노드로 이어진다.

리뷰에서 바꾼 것:

- **표현 디코딩은 지연 실행.** 중단되지 않은 전환은 요소를 측정하거나 조상을 훑거나 프레임마다 codec을 돌리지 않는다. 스냅샷을 찍을 때(현재 시각 주변 두 프레임)와 이어받은 표현을 새 키프레임에 녹일 때만 codec을 쓴다.
- **복원 트랙은 소유권을 뺏지 않는다.** 복원은 transform/opacity만 기본값으로 되돌리므로, 이전 효과가 계속 그 요소를 소유하고 자기 정리(`will-change`, `contain`, clip, z-index)를 그대로 수행한다. 복원이 남긴 인라인 값도 원래 없던 자리면 지운다.
- **살아남는 페이지의 자식은 따로 퇴장시키지 않는다.** 자식은 페이지에 속한다.
- **비행이 다른 노드로 옮겨간 영속 원본은** 그 정체성을 든 실행이 정리될 때까지 숨긴다(기존 opacity lease 사용).
- **소유권은 이전 준비를 무효화하기 전에 찍는다.** 곧 다시 나갈 페이지를 이전 실행의 정리가 숨기지 않도록.
- **핸드오프에 시작 장벽 없음.** `WebAnimation`이 첫 seek 전에 `ready`와 rAF 두 번을 기다리지 않는다. 생성된 프레임에 0ms 프레임이 그려지고, 다음 프레임부터 프레임 페이싱 클럭이 seek하며(그 렌더링 업데이트에서 인라인 시작 스타일도 지움), WAAPI에 넘길 때는 한 프레임 늦게 풀리던 `play()` 대신 `startTime`을 대입한다. 움직이던 요소가 핸드오프에서 멈추지 않고(이전엔 3프레임 정지 + 두 배 스텝), 모든 전환 시작이 3프레임 빨라졌다. 긴 프레임을 33ms로 clamp하는 정지 보호는 그대로다.

남은 한계: clip·filter·색처럼 기본값을 모르는 채널은 이전 효과의 정리값으로 튄다. `prepareHandoff()`는 다음 prepare 동안 진행 중인 전환을 멈추므로, 느린 비동기 prepare는 정지로 보인다(측정값이 어긋나는 것보다는 낫다고 판단).
