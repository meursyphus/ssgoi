# SSGOI with React and Next.js

Use one provider, tell it how to read Next.js's route through `framework`, and
import `SsgoiLayoutBoundary` from the root `@ssgoi/react` entry. Next.js App
Router 13.4–16 is supported; `@ssgoi/react` never imports `next` itself.

Framework index: https://ssgoi.dev/llms/frameworks.txt

## Install

```bash
npm install @ssgoi/react
```

Shell class strings below are Tailwind shorthand. Without Tailwind, apply
`position: relative; z-index: 0; min-height: 100dvh; overflow-x: clip`. Use
`clip`, not `hidden`: `overflow-x: hidden` makes the wrapper the scroll
container, and scroll restore then targets the wrong element. Fall back to
`100vh` only where `dvh` is unsupported.

## Provider

```tsx
// app/ssgoi-provider.tsx
"use client";

import { type ReactNode } from "react";
import { usePathname, useSelectedLayoutSegments } from "next/navigation";
import { Ssgoi, type SsgoiFramework } from "@ssgoi/react";
import { drill } from "@ssgoi/react/view-transitions";

const config = {
  transitions: [{ on: "/**", except: "/", transition: drill() }],
};

const INTERCEPTION_PREFIX = /^(?:\(\.\.\.\)|\(\.\.\)|\(\.\))+/;

const framework: SsgoiFramework = {
  useRoute: () => {
    const pathname = usePathname();
    // The page the children slot renders. During a soft intercept it is still
    // the background page, so no background boundary moves.
    const segments = useSelectedLayoutSegments();
    if (pathname == null) return null;
    const renderedPath = `/${segments
      .filter((segment) => !(segment.startsWith("(") && segment.endsWith(")")))
      .map((segment) => segment.replace(INTERCEPTION_PREFIX, ""))
      .filter(Boolean)
      .join("/")}`;
    return { pathname, renderedPath };
  },
};

export function SsgoiProvider({ children }: { children: ReactNode }) {
  return (
    <Ssgoi config={config} framework={framework}>
      {children}
    </Ssgoi>
  );
}
```

Keep `config` and `framework` at module scope so both stay stable. The
provider file is a client component, so passing a function is fine. The
first (depth-0) boundary calls `useRoute` and shares the route with every
boundary inside it; return `null` while the router is not ready (a null pathname in a
mixed app/pages project), so no guessed route is registered.

`renderedPath` is the path the `children` slot of the layout rendering the
first boundary actually shows. During a soft intercepted modal the URL points
at the modal while the slot still shows the background, so boundaries keep the
background mounted. Put the first `SsgoiLayoutBoundary` in the same layout as
`<Ssgoi>` (here the root layout, as below), and render `{modal}` slots outside
boundaries.

## Layout boundary

No local component is needed, and `SsgoiLayoutBoundary` takes no SSGOI props.
Its id is the route path. Its key is the `config.layouts` scope that matches at
its depth (the number of boundaries above it), or the route path. The first
boundary wraps itself in `Suspense` for Cache Components and renders nothing
until the route is known; content outside it, such as `{modal}`, renders as
usual. It targets App Router; use the manual guide for Pages Router.

It throws an `SSGOI:` error if the nearest `<Ssgoi>` has no `framework`.

```tsx
import { SsgoiLayoutBoundary } from "@ssgoi/react";

<SsgoiLayoutBoundary>{children}</SsgoiLayoutBoundary>
```

## Layout

```tsx
// app/layout.tsx
import { type ReactNode } from "react";
import { SsgoiLayoutBoundary } from "@ssgoi/react";
import { SsgoiProvider } from "./ssgoi-provider";

export default function RootLayout({ children }: { children: ReactNode }) {
  return (
    <html lang="en">
      <body>
        <main className="relative z-0 min-h-dvh overflow-x-clip">
          <SsgoiProvider>
            <SsgoiLayoutBoundary>{children}</SsgoiLayoutBoundary>
          </SsgoiProvider>
        </main>
      </body>
    </html>
  );
}
```

## Boundary options

- `as`: wrapper element or React component; defaults to `div`. Custom components
  must forward DOM attributes to their root.
- DOM attributes (`id`, `className`, `style`, events, `aria-*`, `data-*`) pass through.
  HTML `id` is not the transition id. The boundary owns `data-ssgoi-transition`
  and its React `key`; do not set `key` yourself.

Persistent layouts are declared in config, not on the boundary. For a shop
section with header and tabs, add `layouts: [{ paths: "/shop/**" }]` and put
a boundary around the changing content in `app/shop/layout.tsx`: the root
boundary keeps one key for every shop route, the inner one swaps. For a
per-project shell, `{ paths: "/projects/:id/**" }` gives each project its own
instance. Full patterns: https://ssgoi.dev/llms/complex-routing.txt

## Next.js Cache Components: SsgoiPageBoundary

Use this only when `next.config` sets `cacheComponents: true` and you want
visited routes kept alive. In that mode the App Router keeps a route you leave
mounted inside React `<Activity>` and hides it, so its state is still there
when the user comes back. `SsgoiLayoutBoundary` changes its React `key` to
force a remount, which throws that state away. `SsgoiPageBoundary` never sets
a `key`: Next hides the route you leave and reveals the one you open, and SSGOI
animates the hide out and the reveal in.

`SsgoiPageBoundary` comes from the root `@ssgoi/react` entry and uses the same
`<Ssgoi framework={framework}>` provider as above; nothing changes in it. Like
the layout boundary it takes no SSGOI props (`as` and DOM attributes pass
through), reads `framework.useRoute` itself, renders nothing until the route is
known, and throws if `<Ssgoi>` has no `framework`. Its id is the route's
`pathname`; it ignores `renderedPath` and keys nothing.
A custom `as` component must forward its `ref` to its DOM root, or the id never
updates after the first render.

Beta limitation: while a soft-intercepted modal is open, the background
boundaries' id follows the URL (the modal's path). Nothing remounts or animates
behind the modal; only the id changes until it closes.

The structure changes in two places compared with the layout boundary setup:

1. The root layout keeps `<SsgoiProvider>` but no boundary.
2. Every route-group layout wraps its whole content in `<SsgoiPageBoundary>`,
   persistent chrome such as a bottom nav included, so the nav leaves with its
   group. Every page also wraps itself in `<SsgoiPageBoundary>`.

`config.layouts` is not used in this mode; `config.transitions` works as usual.
Do not wrap intercepted `@modal` pages.

```text
app/
├─ layout.tsx                  <SsgoiProvider>{children}</SsgoiProvider>, no boundary
├─ (top-level)/layout.tsx      <SsgoiPageBoundary> children + <BottomNav /> </SsgoiPageBoundary>
│  ├─ posts/page.tsx           <SsgoiPageBoundary> page </SsgoiPageBoundary>
│  └─ profile/page.tsx         <SsgoiPageBoundary> page </SsgoiPageBoundary>
└─ (detail)/layout.tsx         <SsgoiPageBoundary>{children}</SsgoiPageBoundary>
   └─ posts/[id]/page.tsx      <SsgoiPageBoundary> page </SsgoiPageBoundary>
```

```tsx
// app/(top-level)/layout.tsx
import type { ReactNode } from "react";
import { SsgoiPageBoundary } from "@ssgoi/react";
import { BottomNav } from "@/components/bottom-nav";

export default function TopLevelLayout({ children }: { children: ReactNode }) {
  return (
    <SsgoiPageBoundary className="flex min-h-dvh flex-col">
      {children}
      <BottomNav />
    </SsgoiPageBoundary>
  );
}

// app/(top-level)/posts/page.tsx
import { SsgoiPageBoundary } from "@ssgoi/react";

export default function PostsPage() {
  return <SsgoiPageBoundary>{/* page content */}</SsgoiPageBoundary>;
}
```

| Navigation | Result |
| --- | --- |
| tab → tab | the group stays visible; only the page boundary swaps, BottomNav stays |
| tab → detail | the whole `(top-level)` group is hidden, so it leaves with BottomNav |
| detail → detail | the `(detail)` group stays; only the page swaps |
| Back | the hidden route is revealed with its state intact and animates in |

A group boundary's id follows the route while the group is visible and freezes
while it is hidden, so the group leaves as the route the user left from.

Wrap the boundary once in your own screen component (for example an
`AppScreen` that every page returns) so no page can forget it. Do not mix
`SsgoiLayoutBoundary` and `SsgoiPageBoundary` in the same region: a layout
boundary's key change remounts the routes that page boundaries rely on staying
alive.

## Interception and middleware / proxy

The component manages DOM lifetime. Your application still owns intercepted
route files, parallel slots, and any middleware/proxy redirects or rewrites.
Middleware is called `middleware.ts` in Next 13–15 and `proxy.ts` in Next 16+.
No SSGOI middleware is required for ordinary App Router navigation.

If you already rewrite or redirect, review the matcher and rules for both
client navigation (including RSC/prefetch requests) and direct entry. Avoid
turning an intended soft interception into a redirect/full document load. When
forwarding request headers, retain the existing headers instead of rebuilding
them from only application headers. Keep authorization checks on the server.
Do not install a generic interception rewrite: it depends on your route tree.

For `@modal`, render the slot outside the boundaries. `renderedPath` keeps the
background boundaries on the slot's route, so opening the modal does not
remount the background. Add `default.tsx`/slot fallback routes
as required by Next.js. Verify click → modal, close/back → unchanged background,
and reload/direct URL → full page. See the focused example:
https://ssgoi.dev/llms/complex-routing.txt

Rewrites can make server and browser pathnames differ. Suspense alone does not
fix rewrite hydration mismatches. Scope the boundary to a stable owned slot
when possible, or use a custom wrapper with a stable server fallback as in
Next.js's rewrite guidance; do not defer every navigation key to an effect.
